# План наступної лабораторної: Cognito Managed Login

План складено за умовами лабораторної, файлом викладача `architecture-migration.md` і поточним кодом SuccessfulSuccess. Це план робіт; реалізація та деплой ще не виконані.

## 1. Що потрібно здати

- URL власного сайту `/login/`, який починає OAuth-вхід і перенаправляє на Cognito Managed Login.
- На сторінці Cognito одночасно доступні email/password, самостійна реєстрація та Continue with Google.
- Після обох способів входу браузер повертається на сайт, а email видно без відкриття меню у шапці.
- Два скриншоти сайту: після входу паролем і після входу Google.
- Посилання на коміт із шаблоном інфраструктури та змінами фронтенду.
- Google OAuth-застосунок має статус In production; викладач може зареєструватися власним email або увійти власним Google-акаунтом.
- Підготовлені пояснення міграції, витрат і механізму авторизації для обговорення на занятті.

Файл викладача описує історію його демопроєкту. Його домени, назви стеків, виконані видалення ресурсів і розділ Remaining steps не є фактами про наш AWS-акаунт. Частини 1–2 лабораторної передбачають аналіз міграції; переносити наш працюючий ECS-деплой на Lambda лише заради повторення історії не потрібно. Стан власного деплою спочатку перевіряємо.

## 2. Наша стартова точка

У коді вже є:

- FastAPI, SQLAlchemy, PostgreSQL і Alembic.
- Next.js, статичний експорт для S3/CloudFront і Docker Compose для локальної роботи.
- Cognito User Pool, public app client, домен та умовний Google IdP у `infra/auth.yml`.
- Власні форми входу/реєстрації через AWS Amplify; головна сторінка `/` зараз є сторінкою входу.
- Передавання access token до API, перевірка JWT на бекенді та ізоляція зустрічей за Cognito sub.
- Синхронізація профілю через `/api/v1/me/sync`.

Відмінності від завдання:

- Немає окремого `/login/` із переходом на Cognito для обох способів входу.
- Використовується Amplify замість зазначених у завданні `react-oidc-context` та `oidc-client-ts`.
- Шаблон не задає явно ESSENTIALS, ManagedLoginVersion 2 і ManagedLoginBranding.
- Email користувача зараз знаходиться в меню аватара, а для здачі його потрібно показати у шапці.
- Makefile і GitHub Actions мають ECS-рецепти та заглушки, тоді як README й AWS-шаблони описують Lambda. README-команди `aws-*` відсутні в поточному Makefile.
- У робочій копії вже є сторонні до майбутньої роботи зміни: видалений `.env.example`, змінений Compose і новий CONTEXT.md. Їх не перезаписуємо автоматично.

Основний варіант реалізації: перейти на бібліотеки OIDC з умов лабораторної, залишити наявний бекенд та моделі даних. Одночасно не підтримувати два незалежні джерела auth-сесії.

## 3. Покрокова робота

### Крок 1. Звірити фактичний стан

**Я:** переглядаю Git, конфігурації, наявні auth-ресурси; за доступного AWS-доступу читаю стан стеків, Outputs, доменів, User Pool і client. Зіставляю реальний деплой із документацією. Визначаю, чи оновлюємо наявний pool/client, і перевіряю, чи зміни не спричинять їх заміну.

**Ти:** повідомляєш чинну адресу сайту, репозиторій, AWS-регіон і які доступи вже налаштовані. Якщо доступів немає, входиш у свої AWS/Google/DNS-акаунти. Паролі, AWS keys і Google secret у чат не надсилаєш.

**Результат:** відомо, що працює в AWS, які ресурси потрібно змінити і чи потрібне відновлення деплой-команд. Наявні користувачі та їхні зустрічі збережені.

### Крок 2. Зафіксувати адреси та контракт входу

**Я:** визначаю маршрути `/login/`, `/auth/callback/`, `/today/`, публічну головну сторінку `/` і повернення після виходу на `/`. Публічна головна дає кнопку Sign in; callback і login не потрапляють під RequireAuth. Складаю точний список production/local callback і logout URL з урахуванням trailing slash та реального локального порту. Фіксую Cognito domain prefix, бажано зберігаючи вже наявний.

**Ти:** підтверджуєш власний домен/піддомен та назву застосунку, яка відображатиметься користувачам Google. Якщо домен уже працює, нового не потрібно.

**Результат:** визначені точні адреси для Google, Cognito, фронтенду та CORS. Від цього залежать усі наступні налаштування.

### Крок 3. Підготувати Google OAuth

**Я:** надаю конкретні значення полів Google Console: OAuth origin на Cognito-домені та redirect URI цього домену з `/oauth2/idpresponse`. Готую параметри й приклад конфігурації для credentials.

**Ти:** у власному Google Cloud-проєкті налаштовуєш Branding/Audience, External, назву і контактний email; залишаєш тільки `openid email profile`; створюєш OAuth client типу Web application. Вносиш Client ID і Client Secret локально в gitignored `.env` або погоджене сховище секретів. Публікуєш застосунок зі статусом In production. Якщо консоль вимагає підтвердження домену чи додаткові поля, виконуєш ці кроки у своєму акаунті.

**Результат:** Google-клієнт готовий і має правильний Cognito redirect URI. Цей крок можна робити паралельно з моїми кроками 4–6 після узгодження domain prefix.

### Крок 4. Допрацювати CloudFormation auth

**Я змінюю `infra/auth.yml`:**

- Явно задаю `UserPoolTier: ESSENTIALS`.
- Явно вмикаю self sign-up через `AllowAdminCreateUserOnly: false`.
- Зберігаю email-login, email verification, password policy та PROJECT_NAME tags.
- Задаю `ManagedLoginVersion: 2` для домену.
- Додаю `AWS::Cognito::ManagedLoginBranding`, прив'язаний до app client, з `UseCognitoProvidedValues: true`.
- Зберігаю public client без secret, authorization code flow, scopes `openid email profile`.
- Реєструю production/local callback і logout URL окремо.
- Для фінальної конфігурації забезпечую обох провайдерів COGNITO та Google, правильний порядок створення IdP/client і mapping email/email_verified.
- Google secret залишається NoEcho-параметром і не потрапляє у Outputs або frontend ENV.
- Додаю Outputs, потрібні автоматизованому frontend build.

**Ти:** завершуєш Google-крок; якщо AWS-доступ відсутній або протермінований, відновлюєш його.

**Результат:** повторюваний інфраструктурний шаблон; після його застосування Cognito може показувати керовану сторінку з двома способами входу. Важливий контроль — CloudFormation change set не замінює наявний User Pool без окремого плану перенесення користувачів.

### Крок 5. Перевести фронтенд на OIDC

**Я:**

- Додаю `react-oidc-context` і `oidc-client-ts`, оновлюю package lock.
- Переписую `lib/auth.ts`, `components/auth-provider.tsx` та інтеграцію у providers на єдину OIDC-сесію.
- Налаштовую authority, client_id, scope, response_type code і PKCE через бібліотеку.
- Додаю `app/login/page.tsx`: одноразовий signinRedirect під час відкриття, стан очікування і можливість повторити невдалий вхід.
- Додаю `app/auth/callback/page.tsx`: завершення входу, очищення OAuth-параметрів адреси і перехід на `/today/`; обробка помилки state/callback без циклу редиректів.
- Замінюю власну password-форму на публічну головну з кнопкою Sign in. Пароль і Google-вхід обробляє Cognito.
- Зберігаю контракт useAuth, де це допомагає мінімізувати зміни інших компонентів, і переналаштовую RequireAuth.
- Показую email безпосередньо в app-header/user-menu та кнопку Sign out.
- Для виходу очищую локальну сесію і React Query cache, перенаправляю на Cognito `/logout` з client_id і дозволеним logout_uri.
- Забезпечую завершення callback лише один раз, оновлення сесії та коректне повернення до входу після її завершення.

**Ти:** на цьому етапі не пишеш код; можеш завершувати Google Console.

**Результат:** один auth-механізм і весь передбачений лабораторною сценарій входу/виходу.

### Крок 6. Зберегти наявний захист API

**Я:** адаптую `frontend/lib/api.ts` до отримання OIDC access token; зберігаю `Authorization: Bearer`, `/api/v1/me/sync` з ID token і перевірку відповідності sub. Перевіряю очищення кешу між різними користувачами та JWT-перевірку бекенду. Налаштовую отримання JWKS для конкретного способу деплою: Lambda у VPC без інтернету не зможе завантажити їх сама.

**Ти:** не маєш окремих дій.

**Результат:** stretch goal із захистом API зберігається після зміни фронтенд-бібліотеки; зустрічі залишаються прив'язаними до правильного користувача.

### Крок 7. Зробити деплой повторюваним

**Я:** допрацьовую Makefile відповідно до фактичного AWS-деплою, відновлюю потрібні local/check/auth targets. Додаю читання auth Outputs та API URL, передавання build-time ENV, статичну збірку, завантаження в S3 та CloudFront invalidation. За потреби допрацьовую `frontend/Dockerfile` і Compose ENV. Готую синхронізацію Cognito callback/logout адрес після створення frontend distribution. Оновлюю README/CONTEXT і безпечний `.env.example`, враховуючи його поточне видалення.

Порядок для нового serverless-оточення: базовий auth із відомими local/production адресами → ECR/backend → frontend distribution → оновлення auth-адрес, якщо CloudFront URL був невідомий → frontend build з Outputs → upload/invalidation → точний backend CORS. Для наявного робочого сайту: оновити auth → перебудувати frontend → оновити backend лише за зміни client_id/JWKS/CORS.

**Ти:** забезпечуєш доступ до AWS; DNS-записи додаєш у своєму провайдері тільки якщо домен/сертифікат ще не готові.

**Результат:** конфігурація не залежить від ручного копіювання pool/client IDs. Якщо чинний workflow запускає непрацюючі ECS-команди, узгоджую його з цими ж Makefile targets та OIDC-доступом. Повна перебудова CI не є окремою обов'язковою частиною цієї лабораторної.

### Крок 8. Перевірити перед публікацією

**Я:** перевіряю ESLint, TypeScript, production static export, коректність CloudFormation і значущі auth/API-тести. Перевіряю, що `/login/` та `/auth/callback/` існують у статичному експорті й доступні через CloudFront rewrite. Перевіряю відсутність secrets у diff/build, email у шапці, передачу правильного типу токена, обробку 401 і відсутність auth-циклів.

**Ти:** входиш у тестові акаунти та вводиш поштові коди там, де без тебе перевірка неможлива.

**Результат:** зміни готові до AWS-застосування. Автоматична перевірка не замінює фінальні два реальні входи.

### Крок 9. Застосувати та перевірити як сторонній користувач

**Я:** застосовую готові зміни у визначене середовище за наданого доступу; перевіряю stack outputs, доступність сайту, callback, CORS і поведінку API. Якщо проблема виникає, виправляю конкретну причину і повторюю відповідну перевірку.

**Ти:**

1. У приватному вікні відкриваєш `/login/`, реєструєшся email/password, вводиш код і перевіряєш повернення на сайт з email у шапці.
2. Виходиш і повторно входиш паролем.
3. В іншому приватному вікні входиш через Continue with Google, бажано акаунтом поза списком test users.
4. Перевіряєш статус In production у Google Console; успішного входу одного акаунта недостатньо для підтвердження цього статусу.
5. Перевіряєш email у шапці та вихід. Парольний і Google-акаунти можуть мати однаковий email, але різні sub і різні набори зустрічей — автоматичного об'єднання не додаємо.

**Результат:** викладач зможе виконати ті самі сценарії зі своїми обліковими даними.

### Крок 10. Підготувати здачу та пояснення

**Я:** готую зрозумілий diff/коміт auth-інтеграції, оновлюю інструкцію, збираю checklist і точні посилання. Якщо Cognito був доданий у попередньому коміті, чесно позначаю, що новий коміт завершує відповідність цій лабораторній, і за потреби додаю посилання на початкову інтеграцію. Не переписую історію для створення штучного «першого додавання» Cognito.

**Ти:** отримуєш два реальні скриншоти після успішних входів; я можу допомогти їх зберегти. Надаєш викладачу доступ до приватного репозиторію, якщо потрібно, і подаєш URL `/login/`, два скриншоти та посилання на коміт.

**Я також:** готую `docs/lab3-notes.md` з поясненнями Fargate/ALB → Lambda, RDS → Aurora, регіону, CORS, callback-залежностей, NAT, PKCE, ID/access tokens, різних sub і сценаріїв вартості. Цифри з матеріалів викладача позначаю як його навчальний розрахунок; актуальні тарифи перевіряю окремо для нашого регіону й акаунта.

**Ти:** повідомляєш реальний режим використання проєкту й обговорюєш пояснення зі мною, щоб захищати лабораторну самостійно.

Окремо перевіряємо питання `/health`: зараз він виконує SELECT 1. Пояснюємо, чому часті перевірки можуть заважати паузі Aurora; також перевіряємо вплив відкритих з'єднань. Якщо моніторинг реально увімкнений, готуємо окремий liveness без БД і readiness із БД. SSM/Secrets Manager, account linking і додаткові інфраструктурні сервіси залишаємо наступними покращеннями, якщо вони не потрібні для поточного середовища.

## 4. Залежності та твоя участь

Основний ланцюжок: стан AWS → адреси → Google credentials + код auth → перевірки → auth deploy → frontend build/deploy → два реальні входи → матеріали здачі.

Твої необхідні дії: доступ до власних акаунтів, вибір/підтвердження домену, Google OAuth і його публікація, введення особистих credentials локально, поштових кодів і паролів під час входу, DNS за потреби, остаточне подання роботи. Код, шаблони, Makefile, тести, документацію та технічну діагностику виконую я.

Для початку реалізації достатньо чинного URL сайту/домену, відомостей про AWS-доступ та статусу Google OAuth-проєкту. Написання й локальна перевірка коду можуть йти паралельно з твоєю роботою в Google Console; фінальні Google-вхід і деплой залежать від готовності credentials і доступів.
