# Lab 3: пояснення для захисту

Це відповіді про **наш** проєкт і про навчальний приклад викладача з
`architecture-migration.md`. Описана там міграція на Lambda й Aurora відбулася
в демопроєкті викладача; наш бекенд наразі залишається на ECS/Fargate з ALB та
зовнішньою PostgreSQL. Не видавати цифри й ресурси демопроєкту за фактичний
рахунок нашого AWS-акаунта.

## Що розгорнуто у нас

- Сайт: приватний S3 через CloudFront,
  `https://d3j8i4re8dhmr8.cloudfront.net/`.
- Вхід: Cognito Managed Login v2 у `us-east-1`, email/password self sign-up і
  Google. Початкова адреса для здачі —
  `https://d3j8i4re8dhmr8.cloudfront.net/login/`.
- Бекенд: старий ECS-сервіс із ALB. 2026-10-07 виправлено health check цільової
  групи з неіснуючого `/api/meeting` на `/health`; ціль стала `healthy`.
  CloudFormation-стек сервісу все ще має `CREATE_FAILED`. Сайт поки не має
  налаштованого HTTPS-маршруту до цього API, а поточна ECS task definition не
  передає Cognito pool/client IDs. Тому зустрічі онлайн недоступні. Це не
  перешкоджає обов'язковій демонстрації входу, але stretch goal API онлайн ще
  не доведений.

## Міграція з матеріалів викладача

- Fargate + ALB замінено Lambda function URL: немає постійної плати за
  запущений контейнер і балансувальник, натомість є холодний старт, ліміт
  тривалості/розміру відповіді та масштабування по одному запиту на інстанс.
  Міграції БД треба запускати окремою дією деплою.
- Постійний RDS замінено Aurora Serverless v2 з паузою: в простої залишається
  плата за зберігання, але перший користувач після паузи чекає відновлення.
  Якщо моніторинг регулярно робить запит до БД, пауза не настає.
- Перехід з Франкфурта до `us-east-1` спростив розміщення ресурсів поруч із
  сертифікатом CloudFront, але збільшив затримку API для користувачів в Україні
  та переніс персональні дані до США. Для реального продукту потрібно окремо
  оцінити вимоги до місця зберігання даних.
- У вихідній схемі браузер звертався до API через той самий CloudFront-домен,
  тож CORS не був потрібний. З прямим Lambda URL з'являються два origin і
  точний список дозволених origin у FastAPI. Повернути один origin можна
  маршрутом `/api/*` у CloudFront з окремим origin для API.
- Lambda у приватній VPC без NAT досягає БД, але не зовнішніх API. Звернення
  до зовнішнього LLM чи Cognito JWKS потребувало б NAT, іншої мережевої схеми
  або передачі потрібних публічних ключів під час деплою. Це ціна відмови
  від постійної плати за NAT.
- Залежність деплою циклічна: frontend потребує API URL, а API — frontend
  origin для CORS. У прикладі викладача спочатку розгортають API, потім сайт,
  тоді звужують CORS. Схожа залежність є у Cognito callback URL: його
  реєструють після отримання адреси сайту, а потім перебудовують frontend із
  Cognito outputs.

## Витрати й поріг вибору

У матеріалах викладача орієнтир для *його* Stage 0 — приблизно $52/місяць у
простою, для Stage 2 — приблизно $0.30/місяць у просте; це розрахунок за
тарифами, які він навів на вересень 2026, не вимірювання нашого рахунку.
Постійні складові Stage 0: ALB, публічні IPv4, Fargate, RDS instance і
storage. ALB та адреси оплачують доступність сервісу, навіть без запитів.
У Stage 2 основними змінними стають час, коли Aurora не спить, запити Lambda
та передача даних. При сталому навантаженні Aurora і Lambda можуть стати
дорожчими за постійні інстанси. Порівнювати треба за фактичними годинами
роботи БД, кількістю/тривалістю запитів, мережею і витратами в Cost Explorer,
а не за тимчасовим Free Tier чи рекламним кредитом.

Наш `/health` виконує `SELECT 1`. Перевірка щохвилини не дала б Aurora
заснути. Перед міграцією на Aurora потрібно винести liveness-маршрут без БД,
а перевірку готовності з БД запускати лише там, де вона потрібна. Поточний
ALB перевіряє `/health` кожні 30 секунд, тому це особливо важливе майбутнє
покращення.

## Як працює авторизація

- `/login/` запускає authorization code + PKCE. Браузер зберігає випадкові
  `state` і `code_verifier`; скопійоване пряме посилання на Cognito `/login`
  не має цього стану у новому браузері й не завершить callback коректно.
- Public app client не має secret, бо JavaScript у браузері не може його
  приховати. PKCE прив'язує отриманий authorization code до браузера, який
  почав вхід. Google client secret, навпаки, зберігається на серверному боці
  Cognito й не входить у frontend build.
- ID token містить профіль і email для шапки/синхронізації користувача.
  Access token передається API як `Authorization: Bearer`. API сам перевіряє
  підпис, `exp`, `iss`, `token_use=access` і `client_id`; перевірка лише у
  frontend легко обходиться прямим HTTP-запитом.
- Google і парольний вхід дають різні Cognito `sub` навіть за однакового
  email. Таблиці `users` і `meetings` прив'язують дані до `sub`, тому зустрічі
  лишаються окремими. Автоматично об'єднувати акаунти за email небезпечно:
  спільна або змінена адреса може дати доступ до чужих даних.
- Для публічного Lambda function URL `AWS_IAM` вимагав би підписаних
  AWS-запитів і окремої видачі AWS credentials браузеру. Тут простіше
  перевіряти Cognito access token у FastAPI. API Gateway JWT authorizer міг
  би перенести перевірку на gateway, але додає сервіс і його тарифи.
- Google consent screen показує назву застосунку, домен і запитувані дані.
  Користувач має змогу помітити підроблений домен чи надмірні дозволи до
  підтвердження доступу.

## Стан здачі

- Google-вхід і вихід перевірені у браузері; email видно у шапці.
- У пулі наразі видно Google-користувачів, але окремий підтверджений
  email/password-користувач ще не перевірений. Для цього потрібні власна
  адреса та код із пошти. Скриншоти двох успішних входів слід зберегти після
  перевірки; не додавати в репозиторій паролі, коди чи токени.
- Google OAuth app має статус `In production` за скриншотом користувача.
- Перед здачею перевипустити секрет Google OAuth, який було надіслано в чат,
  оновити його в Cognito та видалити старий. Якщо пароль, показаний на
  скриншоті, був справжнім, його також треба змінити в акаунті власника.
