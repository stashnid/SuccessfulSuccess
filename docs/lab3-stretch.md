# Lab 3 stretch goal: захист API зустрічей

На розгорнутому сайті браузер викликає `/api/v1/*` на тому самому домені, що й
статичний frontend. CloudFront передає `/api/*` чинному ALB та ECS-контейнеру,
вимикає кеш для цих запитів і передає заголовок `Authorization`. Frontend
надсилає Cognito **access token** як `Bearer` для кожного API-запиту. FastAPI
перевіряє підпис через JWKS пулу користувачів, строк дії, `iss`, `client_id` і
`token_use=access`. Ключі кешуються в процесі та перечитуються при зміні `kid`.
Запит без чинного токена повертає 401. Записи зустрічей належать `sub` токена;
чужий запис не відкривається за відомим ID.

Поточна інфраструктура цього студентського проєкту все ще використовує ECS й
ALB з Lab 2. Файл викладача `architecture-migration.md` описує міграцію
*демонстраційного* застосунку на Lambda; це матеріал для аналізу, а не поточний
стан нашого AWS-акаунта. Тому в цій реалізації HTTPS завершується на
CloudFront, після чого він звертається до наявного HTTP listener ALB.

## Відповіді на запитання лабораторної

**Чому токен перевіряє backend?** Перевірку лише у frontend можна обійти:
адреса API та JavaScript видимі всім, і нападник може сам надіслати HTTP-запит.
Backend повинен відхилити підроблений, прострочений або чужий токен та
обмежити дані власником із перевіреного `sub`.

**Чому не `AuthType: AWS_IAM` для Lambda function URL?** Це інший механізм:
він очікує підписані SigV4-запити від IAM-принципала. Cognito access token
користувача не є IAM-ключами; видавати довгострокові AWS-ключі браузеру не
можна. У нашій поточній архітектурі Lambda URL взагалі немає.

**Що змінив би JWT authorizer в API Gateway?** Він перевіряв би підпис,
issuer та audience до виклику backend, зменшуючи власний код перевірки токена.
Backend усе одно має визначати власника зустрічі й застосовувати правила
доступу. Додавання API Gateway означало б окремий сервіс, налаштування
маршрутів та плату за API-запити; наявний CloudFront-маршрут для цієї
лабораторної обходиться без нього.

## Відтворення розгортання

З поточного стану AWS: `make configure-backend-auth`, `make connect-api`,
`make deploy-frontend`. Перший крок бере публічні Cognito ID зі стека
`successfulsuccess-auth` і оновлює task definition, зберігаючи чинні значення
на кшталт `DATABASE_URL` у захищеному тимчасовому файлі, який видаляється після
запиту AWS. Другий крок додає CloudFront origin та behavior `/api/*`; третій
публікує frontend із відносними API-адресами.

## Перевірка

- Запит `GET /api/v1/meetings` через CloudFront без токена повернув **401** з
  кодом `unauthorized`.
- CloudFront-маршрут `/api/*` використовує `Managed-CachingDisabled` та
  `Managed-AllViewerExceptHostHeader`; перша політика запобігає видачі
  персональної відповіді іншому користувачу, друга передає токен.
- Запит з `Bearer invalid-token` також повернув **401**.
- Після входу університетським Google-акаунтом браузер отримав **200** для
  списку зустрічей та синхронізації профілю. Створення тестової зустрічі через
  форму завершилося успішно; вона відобразилася у списку.
